# قائمة تنفيذ لوحة إدارة إمبراطورية الأعمال

## 1. إعداد حساب المشرف والدخول
- [ ] عند أول زيارة، إذا لم يكن هناك حساب مشرف، تعرض الواجهة إعدادًا لإنشاء الحساب الأول ببريد إلكتروني وكلمة مرور ورمز تفعيل سري لمرة واحدة؛ بعد نجاحه يُستهلك الرمز ويُقفل التسجيل نهائيًا.
- [ ] تسجيل الدخول اللاحق يكون بالبريد وكلمة المرور فقط، من دون تسجيل دخول Manus أو تسجيل دخول بحساب اللعبة.
- [ ] يتحقق الخادم من الجلسة والصلاحية في كل طلب؛ لا يعتمد على إخفاء الأزرار أو دور يرسله المتصفح. تُخزن كلمة المرور كقيمة مشتقة آمنة، ويُخزن معرّف الجلسة بصورة غير قابلة لإعادة الاستخدام من قاعدة البيانات.
- [ ] لا يُرسل مفتاح Supabase الخاص أو أي مفتاح توقيع إلى المتصفح أو ملفات المصدر العامة.
- [ ] قبل النشر العام، أضف حدًا لمعدل المحاولات على مستوى IP بالإضافة إلى القفل الحالي لكل بريد إلكتروني.

## 2. البحث عن اللاعب وعرض بياناته الضرورية
- [ ] يدعم البحث بمعرف اللاعب `BE-…` المشتق من `game_profiles.user_id`؛ هذا هو معرف حساب Supabase الذي يمرره التطبيق إلى `accountCodeFromSeed`، وليس معرف العالم داخل ملف الحفظ.
- [ ] يتطابق مولّد BE في قاعدة البيانات مع صيغة التطبيق، بما فيها أخذ آخر خمسة أحرف من المقطع الثاني.
- [ ] تعرض نتيجة البحث اسم اللاعب وآخر مزامنة وأرصدة المال والذهب والماس والشارات اللازمة للإدارة فقط.
- [ ] لا تعرض البريد الإلكتروني أو كلمة المرور أو رموز الجلسة أو نسخة الحفظ الخام أو معرّفات داخلية غير لازمة.
- [ ] قد يُزيل البحث تلقائيًا الشارات الإدارية المنتهية ويضيف ذلك إلى سجل التدقيق؛ يظهر هذا الأثر للمشرف قبل البحث.

## 3. تعديل الأرصدة مع مراجعة وتدقيق
- [ ] يستطيع المشرف المخوّل منح أو خصم المال والذهب والماس مباشرة من بيانات اللاعب المرتبطة بالتطبيق.
- [ ] سبب التعديل إلزامي؛ وتُعرض قيمة كل مورد قبل التعديل وبعده قبل التأكيد.
- [ ] تُرفض القيم غير الصالحة والخصومات التي تجعل أي رصيد سالبًا.
- [ ] عند خصم الذهب، تُحسب القيمة الدفترية مثل اللعبة: تُقرّب حصة الأساس المحذوف إلى أقرب عدد صحيح ثم تُطرح؛ وعند حذف كامل الذهب يُحذف كامل أساس تكلفته.
- [ ] تُنفذ التعديلات بمعاملة ذرية وبمفتاح منع تكرار؛ لا يُطبّق الطلب نفسه مرتين ولا يُترك تعديل جزئي.
- [ ] يسجل كل تعديل المشرف واللاعب والوقت والسبب والقيم السابقة والجديدة في سجل تدقيق غير قابل للتغيير من واجهة الإدارة.
- [ ] لا تُنفذ أثناء التطوير أو الاختبار أي منحة أو خصم فعلي على حساب لاعب إنتاجي.

## 4. إدارة الشارات
- [ ] يمكن منح وإلغاء شارات VIP، وتوثيق الحساب الرسمي للعبة، وعلامة V الذهبية للشريك/صانع المحتوى المعتمد.
- [ ] يُطلب سبب لكل منح أو إلغاء، وتُعرض حالة الشارة قبل وبعد، ويُسجل كل إجراء في التدقيق.
- [ ] تدعم اللوحة مدة الشارة عند الحاجة، وتحتفظ بسجل الشارات المنتهية أو الملغاة بدل حذفها نهائيًا.
- [ ] لا تُمنح شارة المتصدر الأسبوعي يدويًا؛ تصدر آليًا من نتيجة الموسم الخادمية، وتبقى نشطة سبعة أيام ثم تنتقل إلى السجل.

## 5. توليد أكواد المكافآت
- [ ] تحتفظ اللوحة الجديدة بتوليد أكواد المكافآت المتوافقة مع التطبيق والأكواد الصادرة سابقًا.
- [ ] لا تتغير صيغة الكود أو مفتاح التوقيع الحالي قبل التحقق من توافق الاسترداد ومن المصدر الحالي للمفتاح.
- [ ] يبقى مفتاح التوقيع على الخادم فقط، مع تحقق الخادم من المدخلات والانتهاء وحفظ سجل الإصدارات.
- [ ] يظل إصدار الأكواد مقفولًا إلى أن يُستعاد مفتاح التوقيع الخاص الأصلي؛ وظيفة `reward-code` الحالية في Supabase مخصصة للاسترداد ولا تحتوي مسار إصدار.

## 6. الواجهة وتسليم اللوحة
- [x] بُنيت واجهة عربية RTL متجاوبة مع ألوان وهوية اللعبة المعتمدة (الكحلي والزمردي والذهبي ولمسات مرجانية)، واجتازت فحص TypeScript وبناء الإنتاج.
- [x] تستخدم الواجهة رموزًا متمايزة للشارات: كأس ذهبي للمتصدر الأسبوعي، تاج زمردي لـVIP، درع أزرق للتوثيق الرسمي، وV ذهبية للشريك.
- [x] أُنشئت لوحة جديدة مستقلة؛ لم تُحذف أو تُستبدل لوحة إصدار الأكواد الحالية.
- [x] لم تُنشأ قائمة المتصدرين؛ قبل تصميمها يجب طلب صورة توضيحية من المستخدم.
- [ ] لا تُنشر اللوحة ما دام إنشاء الحساب الأول متاحًا؛ ينشئ المستخدم حساب المشرف من Preview أولًا، ثم يُقفل الإعداد وتُنشر اللوحة إن طلب ذلك.

## 7. المرحلة التالية بعد إتمام لوحة الإدارة (طلب المستخدم)
- [ ] في تطبيق اللعبة، اجعل معرف BE قابلًا للنسخ بالضغط عليه وأظهر تأكيدًا واضحًا للنسخ.
- [ ] أضف صفحة بروفايل للاعب ضمن تطبيق اللعبة.
- [ ] بعد إنهاء التعديلات والتحقق منها، ابنِ APK صالحًا للتثبيت وسلّمه للمستخدم.

## حالة التحقق حتى الآن
- نجح `/api/health` وقراءة حالة الإعداد؛ ويُرفض رمز إعداد تجريبي غير صحيح برمز HTTP 403.
- تطابق BE اختُبر على UUID اصطناعي مع صيغة اللعبة، وتطابق تقريب أساس الذهب في مثال بيع ثلث كمية بقيمة أساس 100 (الناتج 67).
- لم يُنشأ حساب المشرف بعد، ولم تُنفذ أي عملية بحث أو تعديل على لاعب حقيقي أثناء الاختبار.
